# 여러 매장의 QR 접수·순번 알림·운영 관리를 개발하는 계획

여러 동네 미용실이 함께 사용하는 매장별 QR 접수와 운영 관리 서비스를 만든다.
손님은 QR로 설치 없이 접속하여 여러 시술과 스타일·색상을 선택한다. 태블릿 접수도 제공한다.
원장은 접수·시술 상태와 오늘의 운영 지표를 관리한다. 유선전화 안내는 후속 확장으로 유지한다.
현재 상태는 개발 전 초안이다. 수요, 하드웨어 호환성, 성능은 아직 검증하지 않았다.
P1 매장별 데이터와 대기 계산, P2 QR 접수·알림·운영 화면, P3 실제 전화 연동 순서로 진행한다.
2026-10-17 추가 요구사항은 Appendix F에 통합했다. 세부 요구사항 충돌 시 Appendix F를 우선한다.

## How to read this

One box is one unit of work. Each box names the evidence. Check a box only when its evidence exists.
이 문서는 pstack의 계획 형식을 소규모 부업에 맞춰 적용한 실행 초안이다.
실행 시 `playbooks/autopilot-stack.md`를 참고하되 이 세션의 사용자 지시와 실행 환경을 우선한다.
PR 번호는 내부 단계 식별자이며 실제 GitHub PR은 아직 없다. 배포와 병합도 수행하지 않았다.
실행 요청은 이미 받은 것으로 취급한다. 이 초안 이후 별도의 계획 승인 절차를 만들지 않는다.
Tests alone are not sufficient verification. A PR is verified only when its unit, live, and perf boxes are all checked.
독립 검토와 실기기 검증이 끝나기 전에는 출시 준비 완료라고 표시하지 않는다.

## Program checklist

### Arm the program

- [x] 사용자 대화를 기준으로 대상과 범위를 정리한다. 이 문서 첫 문단이 근거다.
- [x] standing orders를 기록한다. 기존 유선전화 안내를 최종 목표로 유지한다.
- [x] installed plugin은 없다. 임시 참조 저장소의 지침을 직접 읽어 적용했다.
- [ ] hourly audit tick은 장기 무인 작업을 시작할 때만 검토한다. 현재는 예약 작업을 만들지 않는다.
- [ ] 단계가 끝나면 새 증거와 남은 문제를 담은 status message를 작성한다.

### Spawn owners

- [x] 제품 범위에 대한 독립 탐색 검토를 한 번 요청한다. 출시 검토로 간주하지 않는다.
- [ ] P1 후 P2, P2 후 P3를 진행한다. 전화 회선 정보 수집은 P1과 함께 할 수 있다.
- [ ] 첫 구현은 한 저장소에서 진행한다. 병렬 작성자가 필요한 경우 작업 경계를 먼저 나눈다.

### PR mechanics

- [ ] 실제 저장소를 확정한 후 브랜치와 PR을 만든다. 현재 사용자 저장소 경로는 제공되지 않았다.
- [ ] 단계별로 변경 코드, 검증 명령, 실행 결과를 함께 기록한다.
- [ ] lint와 typecheck를 실행하고 실패한 결과를 감추지 않는다.

### Verdict and merge

- [ ] 출시 전 독립 검토를 받는다. 불가능하면 미완료로 남긴다.
- [ ] UI 변경의 screenshot과 video를 제시한다. 현재는 화면을 구현하지 않았다.
- [ ] 실제 회선 검증 이전에는 전화 안내 기능을 판매하지 않는다.

### Boot recipe

- [ ] P1은 도메인 테스트를 실행한다. P2부터 실제 두 브라우저 세션과 두 태블릿에서 동작시킨다.
- [ ] UI 자동화 드라이버를 저장소 생성 때 선택한다. 현재 실행 명령은 미확정이다.
- [ ] P3는 시험 회선에서 외부 전화기로 발신하여 실제 안내 음성을 확인한다.
- [ ] 검증 자료는 `evidence/P1`, `evidence/P2`, `evidence/P3`에 기록한다. 고객 개인정보를 넣지 않는다.

**Verify, perf.** Tests alone are not sufficient verification. A PR is verified only when its unit, live, and perf boxes are all checked.

1인 원장도 펌의 대기 시간에 다른 고객을 받을 수 있다. 첫 계산은 한 명씩 순차 시술한다는 가정이다.
동시 시술을 보장하지 않고 원장이 예상 시간을 수정할 수 있게 한다. 병행 시술 모델은 현장 관찰 후 결정한다.
고객 계정 없이 번호표로 시작한다. 문자 알림을 선택한 고객에게만 전화번호를 받는다. 원장의 상태 변경 기능은 별도 권한으로 제한한다.

대기 계산은 신규 손님의 시술 시작까지 남은 시간이다. 신규 손님 자신의 시술 시간은 더하지 않는다.
예를 들어 현재 시술 잔여 10~15분, 앞선 커트 15~20분이면 신규 손님은 약 25~35분을 기다린다.
이 숫자는 계산 예시이며 측정된 정확도가 아니다. 안내 문구에는 현장 상황에 따라 달라진다는 뜻을 포함한다.

권장 데이터 초안은 Shop, Service, Ticket, ActiveSession, QueueSnapshot이다.
Ticket 상태는 waiting, serving, completed, cancelled 중 하나다. completed와 cancelled에서 다시 시작하지 않는다.
QueueSnapshot에는 대기 인원, 시술 여부, 대기 범위, 영업 상태, 갱신 시각, 버전을 포함한다.
통신 heartbeat와 원장의 마지막 상태 입력 시각을 구분한다. 통신이 살아 있어도 시술 예정 시간을 넘긴 채 입력이 없으면 확인 불가로 표시한다.
영업 중, 일시중지, 접수 마감, 영업 종료를 구분한다. 접수 마감 상태의 전화는 신규 방문을 권하지 않는다.
접수 명령에는 shopId와 requestId를 포함한다. 같은 두 값의 재시도는 번호표 한 장만 만든다.

## Appendix F. 여러 매장에 제공할 요구사항을 반영한다

### F1. 제품과 판매 범위를 확정한다

매장 하나에 맞춘 주문 제작이 아니라 매장별 설정으로 운영하는 공통 서비스를 만든다.
첫 업종은 미용실이다. 같은 프로그램에 매장, 메뉴, 옵션, 가격, 시간, 사진, 영업 설정을 추가한다.
다른 업종으로 확장할 수 있도록 공통 접수와 호출을 분리하되, 모든 업종의 스케줄을 처음부터 구현하지 않는다.
매장 도입 때 사장님과 메뉴 구성, 시술 시간, 스타일·색상 예시, 가격 조건을 함께 정리한다.
초기 설정 컨설팅과 소프트웨어 이용료는 구분하여 가격 가설을 만든다. 현재 확정 요금은 없다.
고객 결제, 카드 연동, 정산 기능은 첫 버전에서 제외한다.

### F2. 고객이 QR로 접수하게 한다

- 매장마다 QR과 공개 매장 페이지를 만든다. 접속 첫 화면에 매장명과 접수 가능 상태를 표시한다.
- 회원가입과 앱 설치 없이 시작한다. 손님은 서비스 선택, 선택 확인, 접수 완료 순서로 이동한다.
- 남성 커트와 염색처럼 여러 서비스를 함께 고를 수 있게 한다.
- 선택한 서비스에 필요한 스타일과 색상만 다음 화면에 표시한다. 선택하지 않은 시술 옵션은 숨긴다.
- 사진 카드와 함께 이름을 표시한다. 색상만으로 색 이름이나 상태를 구분하지 않는다.
- 잘 모르겠어요·방문 상담을 선택할 수 있게 한다. 모든 고객에게 스타일 선택을 강제하지 않는다.
- 합계 예상 금액, 예상 시술 시간, 시술 시작까지의 대기를 각각 구분해서 표시한다.
- 길이·모량·탈색 여부처럼 현장 판단이 필요한 조건은 추가요금 가능 또는 상담 후 확정으로 표시한다.
- 접수 완료 후 내 번호, 내 앞 대기 인원, 대기 범위, 알림 상태를 큰 글씨로 표시한다.
- QR 사용이 어려운 고객은 기존 매장 태블릿이나 사장님의 대리 접수로 같은 대기열에 들어간다.
- 공개 링크는 기본적으로 대기 조회만 제공한다. 방문 접수와 원격 줄서기를 구분한다.
- 고정 QR은 촬영·공유될 수 있다. 이를 현장 방문 증명으로 취급하지 않는다.
- 첫 시험은 사장님이 방문 접수를 확인한다. 원격 허위 접수가 많으면 바뀌는 현장 코드 방식을 시험한다.

### F3. 메뉴와 가격·시간을 매장별로 설정한다

Service와 OptionGroup, Option으로 메뉴와 옵션을 표현한다.
단순 합산이 맞지 않는 커트·염색 조합은 매장별 묶음 메뉴 가격과 시간을 지정한다.
염색제 방치 시간과 원장이 손을 쓰는 시간을 구분할 수 있는 데이터 구조를 둔다.
첫 일정 계산은 순차 시술과 수동 보정을 사용한다. 병행 시술 자동 최적화는 실제 운영을 관찰한 후 추가한다.
접수 당시 메뉴명, 선택 옵션, 가격과 시간의 사본을 보관한다. 메뉴 수정으로 이전 접수 금액을 바꾸지 않는다.
원장은 상담 후 최종 금액과 시술 구성을 수정할 수 있다. 수정 이력과 원인을 남긴다.
미확정 가격이 있는 접수는 확정된 매출 합계에 포함하지 않고 상담 필요로 구분한다.

### F4. 순번 알림을 제공한다

접수 완료, 곧 차례, 호출을 구분한다. 도착한 알림이 시술 시작 보장은 아니라는 뜻을 표시한다.
첫 제품은 화면 내 실시간 갱신을 기본 제공한다. 화면을 닫은 고객의 호출은 별도 전송 수단이 필요하다.
문자 알림을 선택 기능으로 설계한다. 전화번호를 받는 화면에 용도와 필요한 동의·보관 안내를 제공한다.
문자 공급사, 발송 단가, 계정과 실발송은 아직 확정하지 않았다. 시험 구현은 전송 어댑터와 가짜 발송으로 시작한다.
웹 푸시는 기기·브라우저·설치·권한 조건이 있으므로 모든 QR 방문자에게 보장하지 않는다.
iOS·iPadOS의 홈 화면 웹 앱과 권한 조건은 Apple 문서를 기준으로 실제 기기에서 확인한다.
알림 실패·미허용·미설정 상태를 사장님이 확인할 수 있게 한다. 전송 성공을 수신·읽음으로 표시하지 않는다.
같은 호출 이벤트를 재처리해도 문자가 중복되지 않도록 이벤트 식별자와 전송 기록을 둔다.
호출 후 미도착, 재호출, 보류, 취소는 사장님이 처리한다. 자동으로 순번을 없애지 않는다.

### F5. 사장님 화면에서 운영을 관리한다

첫 화면에는 현재 대기 인원, 시술 중 인원, 오늘 완료 고객 수, 완료 시술 합계, 실제 시술 시간을 표시한다.
대기 목록에는 메뉴와 주요 옵션을 표시한다. 동작은 호출, 시작, 완료, 보류, 취소를 중심으로 구성한다.
서비스 이용자가 접수한 시점에는 예상 매출만 증가한다. 완료 처리 시 확정한 금액을 완료 시술 합계에 반영한다.
완료 시술 합계는 앱에 기록된 금액이며 실제 수납액이나 순이익이 아니다. 결제 없이 수납 확인을 추정하지 않는다.
취소·보류 접수는 완료 시술 합계에서 제외한다. 완료 내역 정정은 원래 기록과 변경 이력을 남긴다.
업무 시간은 영업 경과 시간, 실제 시술 시간, 남은 예정 시간을 구분한다.
실제 시술 시간은 시작·완료 기록으로 계산한다. 여러 고객을 병행할 때 겹치는 시간을 이중 합산하지 않는다.
매장 현지 날짜를 기준으로 일별 통계를 집계한다. 첫 운영 시간대는 Asia/Seoul이다.
플랫폼 운영자, 매장 소유자, 직원의 권한을 구분한다. 직원의 금액 통계 열람은 매장 설정으로 제한한다.

### F6. 네이버에서 공개 대기 페이지로 연결한다

매장별 공개 페이지에 여유, 혼잡, 매우혼잡, 마감 상태와 마지막 갱신 시각을 표시한다.
상태는 인원수만으로 계산하지 않고 신규 고객의 예상 대기와 접수 가능 여부로 계산한다.
초기 예시는 여유 20분 미만, 혼잡 20분 이상 50분 미만, 매우혼잡 50분 이상이다.
기준은 검증 전 가설이다. 매장별 조정이 가능해야 한다. 마감은 대기가 길다는 뜻이 아니라 신규 접수 중단이다.
휴무·일시중지·정보 확인 불가는 별도로 표시한다. 연결이 끊긴 매장을 여유로 표시하지 않는다.
공개 페이지에는 개인 이름, 연락처, 번호표별 시술 정보와 금액 통계를 내보내지 않는다.
네이버의 매장 소개·홈페이지 등 외부 링크를 등록할 수 있는 위치를 실제 관리 화면에서 확인한다.
링크를 누르면 우리 매장 페이지에서 최신 혼잡도를 보여주는 방식을 첫 대상으로 삼는다.
네이버 검색 결과나 지도 안에 혼잡도를 직접 자동 표시하는 공식 연동은 별도 검증 사항이다.
현재 해당 연동 API와 권한을 확보했다고 가정하지 않는다. 네이버 화면을 자동 조작하여 상태를 수정하지 않는다.

### F7. 전 연령이 사용할 수 있는 화면을 만든다

- 기본 글씨는 충분히 크게, 주요 버튼은 높이 48~56px을 초기 설계 기준으로 잡는다.
- 한 화면에 한 가지 결정을 중심으로 배치한다. 다음과 이전 위치를 고정한다.
- 과한 장식 대신 여백, 높은 대비, 일관된 글씨와 제한된 강조색으로 정리한다.
- 사진에는 텍스트 이름을 함께 제공하고 색상 상태에는 상태 단어를 함께 제공한다.
- 복잡한 시술 조합은 펼쳐서 보여주고 대표 메뉴와 상담 선택을 먼저 제공한다.
- 스마트폰 기본 브라우저, 네이버 내부 브라우저, 10인치 태블릿을 각각 시험한다.
- 연령대가 다른 실제 사용자에게 설명 없이 접수하게 해 본다. 큰 글씨만으로 사용성을 통과했다고 판단하지 않는다.

### F8. 서버와 매장 데이터를 분리한다

AWS 등의 중앙 서버 한 곳에서 매장별 데이터를 분리하는 구조를 권장 초안으로 둔다.
고객용 웹, 사장님용 웹, 공통 API, 관계형 데이터베이스, 알림 전송 작업자로 구성한다.
초기에는 하나의 애플리케이션으로 구현한다. 매장 수 증가만으로 서비스를 여러 개로 분할하지 않는다.
AWS의 구체 서비스, 인스턴스, 비용은 트래픽과 운영 조건을 정한 후 검토한다. 현재 자원을 생성하지 않았다.
미니 서버는 개발·시험 또는 현장 전화 장비 연결에 사용할 수 있다.
집의 미니 서버 한 대로 여러 고객 매장의 전체 서비스를 운영하면 정전·인터넷·복구를 직접 책임져야 한다.
중앙 서버와 매장별 보조 장비의 역할을 구분한다. 첫 버전의 오프라인 중복 접수·자동 병합은 보장하지 않는다.

모든 비공개 데이터에 tenantId를 둔다. 사장님이 보낸 tenantId를 그대로 신뢰하지 않는다.
로그인 사용자와 소속 매장의 권한으로 서버가 접근 범위를 결정한다.
데이터베이스 관계와 고유키에도 매장 구분을 반영한다. 순번과 requestId의 유일성은 매장 안에서 보장한다.
자신의 대기표는 추측하기 어려운 토큰으로 접근한다. 순번 숫자만으로 다른 사람의 내역을 열지 못하게 한다.
매장 A 계정이 URL·요청 값을 바꿔 매장 B의 접수·통계·사진 관리에 접근하지 못하는지 검증한다.

### F9. 구현 순서와 통과 조건을 보완한다

| 작업 | 구현 결과 | 통과 조건 |
| --- | --- | --- |
| P1 매장별 모델 | 메뉴·옵션·조합·대기 상태·접수 사본 | 메뉴 변경이 이전 접수에 영향을 주지 않고 매장 간 데이터가 분리됨 |
| P2a QR 접수 | 고객 선택과 확인, 태블릿과 대리 접수 | 중복 접수 방지, 잘못된 매장 접수 방지, 상담 선택 가능 |
| P2b 원장 화면 | 호출·완료·지표·가격 정정 | 대기 중 금액을 완료 시술 합계로 오인하지 않고 취소와 정정이 반영됨 |
| P2c 알림과 공개 페이지 | 알림 기록·실패 상태·혼잡도 | 기기 제약과 전송 실패가 표시되고 공개 화면에서 개인정보가 노출되지 않음 |
| P2d 여러 매장 시험 | 다른 설정의 매장 두 곳 | 같은 코드로 운영하며 메뉴·통계·권한이 서로 섞이지 않음 |
| P3 전화 안내 | 기존 회선 자동 안내 | 실제 회선·복구·오래된 상태 차단 확인 |

P2a부터 P2d까지 각각 검증 결과를 남긴 후 다음 작업으로 진행한다.
단위 테스트 외에 실제 모바일 화면과 데이터 격리 테스트를 수행한다.
공급사 없는 가짜 알림 시험은 실제 수신 검증을 대체하지 않는다.
이 문서는 요구사항을 갱신한 상태이며 제품 구현·운영·네이버 연동·알림 발송을 완료한 상태가 아니다.
