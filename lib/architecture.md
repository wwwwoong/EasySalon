# Salon service data boundary

The domain is a shop aggregate with a catalog, operating phase, numbered queue and ticket state machine. The Model the Domain principle puts transitions in a table and monetary snapshots in each ticket. Route handlers validate external inputs and never accept an owner identity from the payload.

Two storage designs were considered. Normalized shop, menu, ticket and event tables support large history and indexed reporting. They also require multi-statement transactional changes for the queue's single active stylist invariant. A per-shop JSON aggregate supports one atomic compare-and-swap update on D1. This pilot uses the aggregate. All commands read a revision and update only that revision, with at most five attempts. A concurrent menu update and queue command cannot overwrite each other. Every command rechecks authorization against its latest snapshot.

The D1 shops table is migration-owned. Initialization uses owner-derived deterministic demo IDs and INSERT OR IGNORE, so repeated or concurrent initialization cannot duplicate demo shops. UUID v4 customer request IDs deduplicate within each shop; reusing an ID with a different selection is rejected. Each customer capability token has two random UUIDs. Token lookup runs a server-side JSON search and returns only the matching customer's restricted view. A normalized token index should replace this scan before the shop count grows. The public shop response omits tickets, financials and owner identifiers.

The pilot accepts at most 32 KiB per command, 100 unfinished public tickets per shop, 2,000 retained tickets per shop and 30 catalog services. These are explicit pilot limits, not automatic archival. Production needs an archive and retention policy, per-client abuse controls, customer cancellation credentials and notification delivery workers before wide public enrollment. The current site identity boundary is private; a public customer deployment needs a separate public hostname with the same capability route protections.

The queue supports one stylist. Public QR requests require owner approval and do not affect the published waiting time until approved. A called customer or a serving customer occupies the single stylist slot. Held customers are excluded from the queue. Estimates become unknown when a serving job is overdue or a call goes unanswered for ten minutes. Server time controls all accounting. Revenue means completed service value, not collected payment. Work time is the union of today's service intervals in Asia/Seoul, with cancellation disallowed once service starts. Price edits retain audit entries. Terminal queue states cannot resume. Repeating the same completion or cancellation is harmless. Consultation customers require an explicitly confirmed final price before completion. Approval assigns queue order so pending requests cannot jump previously accepted customers.

No SMS or push integration is claimed. Notifications are in-app call records. Refreshing the customer's ticket retrieves the call state. Menu options use keys such as `color:color` and `mens-cut:style`. Korean congestion labels are 여유, 혼잡, 매우혼잡, 마감, 접수 중지 and 확인 중. Consultations can omit style choices. A cut plus color applies the configured discount with frozen price and duration snapshots. Multi-stylist scheduling and salon-specific combination rules remain later work.

Owners now have one assigned salon. Server listing returns only the first persisted salon for the identity, and management reads, writes, and staff admissions require both its assigned id and stored owner id. Legacy extra samples are retained but inaccessible through management. Initialization uses one deterministic row per identity. Menu removal affects only future admissions; an empty catalog is allowed. Public customer menu/status projections remain separate from private management data.
